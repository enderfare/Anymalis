# Skills

Skills represent broad, learned capabilities that a character can develop through practice, instruction, and experience.

A Skill answers:

> **"What can this character do?"**

Skills are broader than Techniques and more active than Traits.

A character's Skill level represents their developed competence within a defined area.

---

# Skill Structure

Each Skill should define:

```text id="z8s3tq"
Name
Description
Associated Attribute
Uses
Specializations
Mastery
```

Not every Skill requires every field.

---

# Skill and Attribute

Attributes describe a character's underlying capabilities.

Skills describe how those capabilities have been developed and applied.

The same Attribute may support multiple Skills.

Likewise, a Skill may sometimes be resolved using different Attributes depending on the circumstances.

The Attribute represents **how the character approaches the task**.

The Skill represents **what the character knows how to do**.

---

# Skill Categories

Skills may be grouped by their primary function.

These categories are organizational rather than restrictive.

Possible categories include:

* Physical
* Mental
* Social
* Technical
* Survival
* Craft
* Resonance
* Knowledge
* Perception

A Skill may belong to more than one category when appropriate.

---

# Skill Training

Training represents formal or informal development in a Skill.

A character may gain Skill Training from:

* Lineage
* Background
* Instruction
* Practice
* Advancement
* Other character-development systems

A Lineage's standard Skill Training should be connected meaningfully to that Lineage's identity.

Training does not automatically grant mastery.

It establishes that the character has received meaningful development in that Skill.

---

# Skill Proficiency

An individual character's competence in a Skill should be represented through the established Skill progression system rather than through legacy terminology.

Do not use **Proficiency Bonus** as a generic mechanic.

The current system uses **Skill Mastery Bonus** where a numerical mastery bonus is required.

Skill competence should therefore be described through the character's established Skill state and Mastery rather than importing terminology from another rules system.

---

# Skill Mastery

Skill Mastery represents developed competence beyond basic familiarity.

A Skill may progress through increasingly advanced levels of understanding.

The exact numerical progression belongs to the character advancement rules.

Mastery should represent meaningful improvement in the character's ability to perform tasks associated with the Skill.

Mastery may be developed through:

* Practice
* Instruction
* Experience
* Specialized training
* Advancement

---

# Skill Specializations

A character may specialize within a broad Skill.

A Specialization narrows a Skill into a particular field, method, environment, or application.

Examples:

```text
Athletics
└── Climbing

Craft
└── Metalworking

Survival
└── Winter Survival

Knowledge
└── Resonance Theory
```

A Specialization should not become an entirely separate Skill unless it has developed enough breadth to warrant its own system entry.

---

# Skill Specialization Principles

A Specialization should:

* Narrow an existing Skill
* Represent meaningful additional knowledge
* Apply to a recognizable category of tasks
* Have a clear relationship to its parent Skill

A Specialization should not:

* Replace the parent Skill
* Grant unrelated abilities
* Function as a complete character concept
* Automatically grant a Technique

---

# Skill Checks

When a character attempts a task that depends on a Skill, the appropriate Skill resolution system is used.

The resolution should normally account for:

```text id="l4v7xk"
Attribute
+
Skill
+
Relevant bonuses or penalties
```

The exact mathematical formula belongs to the core resolution rules.

Do not create separate resolution formulas inside individual Skills unless the Skill has a genuinely unique mechanic.

---

# Attribute Selection

The most appropriate Attribute may change depending on how a character approaches a task.

For example, the same broad Skill may be used differently depending on the situation.

A physically forceful approach may rely on one Attribute.

A precise approach may rely on another.

A socially manipulative approach may rely on another.

The player and GM should determine the relevant Attribute from the fiction and circumstances rather than assuming that every Skill always maps to exactly one Attribute.

Where a Skill has a commonly associated Attribute, that Attribute should be listed as its default.

---

# Skill vs. Trait

A Skill represents learned capability.

A Trait represents a persistent characteristic.

For example:

**Trait — Night Vision**

The character can see in low-light conditions.

**Skill — Perception**

The character knows how to observe, notice, and interpret details.

The Trait changes the circumstances under which the Skill can be used.

It does not replace the Skill.

---

# Skill vs. Technique

A Skill represents broad competence.

A Technique represents a specific application of that competence.

For example:

**Skill — Athletics**

The character has developed physical movement and exertion skills.

**Technique — Wall Runner**

The character knows a specific method for maintaining momentum while moving across suitable vertical surfaces.

The Technique can depend on Athletics without becoming another Athletics Skill.

---

# Skill vs. Knowledge

Knowledge may be represented as a Skill when it requires active development and can be applied across multiple situations.

Knowledge Skills should represent usable understanding rather than simply possession of isolated facts.

For example:

> Resonance Theory may represent understanding of Resonance principles, Glyph construction concepts, and the interpretation of magical phenomena.

A character does not automatically know every fact within a Knowledge Skill.

The difficulty and specificity of the information still depend on the character's level of expertise and the circumstances.

---

# Skill and Resonance

Resonance-related Skills represent learned methods of interacting with or understanding Resonance.

They do not automatically grant:

* Elemental Affinity
* A Resonant Scar
* Access to an Element
* Access to a Variant
* Spell construction ability

Those capabilities are governed by the Magic System and the character's Resonant Scar where applicable.

A character may therefore possess extensive Resonance knowledge without having natural Elemental Affinity.

---

# Skill and Paths

Each of the Four Paths emphasizes different kinds of Skill development.

### Scribe

Emphasizes:

* Glyph construction
* Magical design
* Analysis
* Preparation
* Precision
* Complex spell construction

### Channeler

Emphasizes:

* Direct Resonance manipulation
* Physical enhancement
* Close combat
* Speed
* Immediate magical application

### Artificer

Emphasizes:

* Resonance engineering
* Construction
* Devices
* Tools
* Materials
* Preparation

### Null

Emphasizes:

* Anti-Resonance techniques
* Disruption
* Cancellation
* Detection
* Control of magical interactions

A Path does not prevent a character from developing Skills outside its traditional focus.

---

# Skill Training and Lineage

A Lineage may provide one Skill Training as part of its standard character package.

The selected Skill should have a meaningful connection to the Lineage.

The Skill Training should represent something commonly taught, practiced, inherited culturally, or developed through the Lineage's typical environment.

It should not be used simply as a numerical bonus.

Examples:

* A maritime culture might commonly train Navigation.
* A craft-focused lineage might commonly train a relevant Craft Skill.
* A highly communal lineage might commonly train a Social Skill.
* A lineage adapted to a difficult environment might commonly train a Survival Skill.

The specific Skill should be determined by the individual Lineage rather than assumed universally.

---

# Skill Training and Background

Backgrounds may also provide Skill Training.

Lineage and Background should remain separate sources.

**Lineage** represents what the character inherits or grows up with through their people.

**Background** represents the particular life circumstances and experiences that shaped the individual.

The same Skill may be trained by both sources when the character's history supports it.

Duplicate training should follow the character-creation rules rather than automatically creating an additional bonus.

---

# Skill Development

Skills develop through the established advancement model:

```text id="h3z8pn"
Practice
    ↓
Instruction
    ↓
Experience
    ↓
Mastery
    ↓
Transformation
```

### Practice

Repeated use develops familiarity and competence.

### Instruction

Formal teaching provides structured development.

### Experience

Real situations reveal weaknesses and allow the character to adapt.

### Mastery

The character demonstrates deep and reliable competence.

### Transformation

The character's relationship with the Skill changes fundamentally.

Transformation should be rare and meaningful.

---

# Skill Failure

Failure on a Skill check does not necessarily mean the character has no knowledge of the Skill.

Failure may instead represent:

* Poor circumstances
* Insufficient time
* Incomplete information
* Physical limitations
* External interference
* Pressure
* An opposing character
* The inherent difficulty of the task

The consequence of failure should follow the normal resolution rules.

---

# Repeated Tasks

Do not require repeated Skill checks when the outcome is already certain or when repetition would add no meaningful uncertainty.

A character with sufficient Skill Mastery should be able to perform routine tasks without unnecessary rolling.

Skill resolution should be reserved for situations where:

* Failure is possible
* The outcome matters
* Circumstances create uncertainty
* Another character or force contests the attempt
* The task presents meaningful difficulty

---

# Skill Breadth

Skills should be broad enough to support multiple situations but narrow enough to remain distinguishable from one another.

A Skill should not contain every possible action related to a theme.

If two Skills consistently overlap, their boundaries should be clarified or the Skills reconsidered.

If a proposed Skill only describes one very specific action, it may instead be:

* A Technique
* A Specialization
* A Trait

---

# Skill Design Test

Before creating or modifying a Skill, ask:

### 1. What broad capability does it represent?

If the answer is one specific action, it may be a Technique.

### 2. Is it learned?

If the capability is inherent, it may be a Trait.

### 3. Can it be developed?

A Skill should support meaningful progression.

### 4. Does it overlap with another Skill?

Define the boundary before adding a new Skill.

### 5. Can multiple Attributes reasonably apply?

If so, establish a default Attribute while allowing the fiction to determine alternatives.

### 6. Can multiple Techniques depend on it?

A healthy Skill should support multiple specific applications.

### 7. Does it work across different characters?

A Skill should describe a capability available to characters generally, even when different characters develop it differently.

---

# Standard Skill Format

Use the following structure when defining a Skill:

```text id="n3x5wj"
# [Skill Name]

## Category
[Primary category]

## Description
[What broad capability the Skill represents.]

## Default Attribute
[Most commonly associated Attribute]

## Uses
[Common applications of the Skill.]

## Specializations
[Examples or established Specializations.]

## Mastery
[How deeper mastery of the Skill is expressed.]
```

---

# Design Principle

Skills are the middle layer of the character system.

They sit between broad character characteristics and specific actions:

```text
Attribute
    ↓
Skill
    ↓
Technique
```

Traits exist alongside this structure as persistent characteristics:

```text
Trait
   ↓
modifies or establishes capabilities
```

A complete character is therefore not defined by a single category.

Instead:

```text
Attributes
    +
Skills
    +
Traits
    +
Techniques
    +
Specializations
    +
Background
    +
Lineage
    +
Path
    +
Resonant Scar
    +
Conditions
```

The purpose of the system is to allow these components to describe different aspects of the same individual without forcing one component to contain the responsibilities of another.
